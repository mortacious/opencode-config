# REPO.md - development rules for this repository

## Layout

- `opencode.jsonc` - main config: providers, per-agent models/variants, plugins list, MCP servers, `experimental.subagent_depth: 2`.
- `agents/*.md` - agent definitions (frontmatter + prompt body). `orchestrator.md` is the PRIMARY main agent (the single entrypoint and `default_agent` in `opencode.jsonc`); its body is the system prompt fed to the main agent every session. The roster is three capability shells: `sidekick` (execution, visual work, commits), `analyst` (read-only generalist: exploration, research, planning, visual inspection, red-team), and `reviewer` (audit gate). The built-in `build`/`plan` primaries are disabled in `opencode.jsonc`. Editing these changes every future session. `analyst.md` is the read-only generalist; its model comes from the `agents.analyst` pin in `opencode.jsonc`, and its permissions grant the ddgs MCP tools and a deny-by-default shell.
- `skills/<name>/SKILL.md` - skill definitions: `create-profile`, `fusion-brainstorming`, `fusion-code-review`, `fusion-commit`, `fusion-delegation-spec`, `fusion-plan-log`, `fusion-planning`, `fusion-research-methodology`, `fusion-sparring`, `fusion-workflow`, `plan-review`, `reflect`, `simplify`. The `fusion-*` skills carry the method knowledge and dispatch templates (including `templates/commit-task.md`, the guarded commit/push execution spec, and `templates/plan-task.md` / `templates/sparring-task.md` for analyst dispatches); agent bodies stay thin shells. `fusion-workflow` is the how-to map: entry points (orchestrator primary, read-only subagents), which skill to load when, and the delegation flow.
- `command/` - custom command directory (slash commands); currently holds `quick.md` only. Drop new command files here.
- `knowledge/web-search-modules/` - search-strategy modules used by the research/web-search flow.
- `plugin-src/fusion-audit/` - local plugin package (deps installed via install.sh, registered as `./plugin-src/fusion-audit` in opencode.jsonc) holding the read-only observability plugin for the Fusion delegation tree. Logs subagent spawns and edit/task tool calls to OpenCode logs under service `fusion-audit`. It does NOT enforce who-does-what; permissions do that.
- `plugin-src/fusion-bootstrap/` - local plugin package (deps installed via install.sh, registered as `./plugin-src/fusion-bootstrap` in opencode.jsonc) that injects a short skill reminder as an extra system part on every primary model request: primaries (orchestrator) are told to check the skill catalog and fill a dispatch template from `skills/fusion-delegation-spec/templates/` instead of freehanding a task spec, and child sessions (any session with a structural `parentID`; detection is cached, a failed lookup injects nothing and retries next request) are told their task prompt is the full specification and their report must open with a `SKILLS:` line.
- `plugin-src/fusion-channel/` - local plugin package (registered as the plain string `./plugin-src/fusion-channel` in opencode.jsonc) holding the steer/report channel: one `/steer` entry point (bare `/steer` opens a picker over the session's direct children with running first, then prompts for the message, while `/steer [agent|session-id] <message>` delivers directly; both call the server-side `steer` RPC registered by the plugin, and a model-callable `steer` tool is the non-TUI path for the same delivery logic - the server deliberately does NOT register a `/steer` command because keymap slash commands and server commands share one prompt completion list, so two registrations would show two entries; every steer appends a `type:"steer"` line to the durable JSON-lines channel log at `~/.local/state/opencode/fusion-inbox.jsonl` and surfaces a synthetic aside to the orchestrating session; the `report` tool writes child -> orchestrator notes/questions/blockers to the same log and mirrors them live; the module is always on).
- `plugin-src/profile-switcher/` - local plugin package (deps installed via install.sh, registered as an options object in opencode.jsonc) for in-session profile switching: the server entry (`index.ts`, plugin id "profile-switcher") exposes the `profile` RPC (list/current/set/populate + `changed`/`populate` events), applies the model subset of `profiles/<name>/opencode.jsonc` overlays as live agent-model transforms with availability fallback, and persists state per window location in `<CONFIG_DIR>/.active-profile` (format v1: an optional machine-wide `global\t<name>` fallback plus one `location\t<absDir>\t<name>` record per directory; the file is shared with `bin/oc`, and a `changed` broadcast converges only instances whose directory matches); on a switch it rewrites tracked sessions' persisted models to the new profile's targets via `session.switchModel`, scoped by TUI window claims (the open tabs) plus this location's `session.created` entries - never another workspace's history - and consent-gated to sessions matching the previous profile's target, with running sessions keeping theirs until idle; the TUI entry (`./tui`, plugin id "profile-switcher.tui") adds the `/profile` slash command, the per-window sidebar `Profile: <active>` indicator, and seeds the location's pre-existing sessions into the server tracker via the populate RPC at setup (relayed through the plugin event bus; `changed` events from other directories are ignored).
- `plugin-src/subagent-view/` - local plugin package (TUI-only; server entry is a no-op stub) that restores the v1-style live subagent visibility removed in v2: a collapsible `Subagents (n)` section in the sidebar (sidebar.content slot, mirrors the built-in MCP section's collapse pattern) listing child sessions of the open session as two-line rows - line 1 is the status marker, agent, and task title (an `@<agent> subagent` title prefix is stripped); line 2 is the model, live token/context usage (`tokens (%)`) and cost (2s polling; network calls only while a child runs). Rows open the child session on click (router navigate - children are not tab-openable), header keeps the true child total, all children are listed and the sidebar's own scrollbox handles overflow.
- `plugin-src/subagent-cap/` - local plugin package (deps installed via install.sh, registered as an options object in opencode.jsonc) that caps concurrent subagent spawn-tool calls per launched profile: options `{max, profiles}` where `max: 0` (the base config value) is unlimited and `profiles["cheap-local"] = 3` caps that overlay; a blocked spawn throws `Tool.Error` with the running/cap counts and the profile name so the calling agent sees why. The counter is per server instance (another window's spawns bypass it).
- `.plans/` (in target projects; never tracked, excluded via `.git/info/exclude`) - per-branch plan/notes document `<branch>.md`: approved plan steps, decisions, progress log, implemented features, open issues, final summary. This repo itself keeps its own `.plans/v2-port.md`.
- `tui.json` - v1 leftover: a separate plugin list loaded only by the v1 TUI; v2 ignores it, and its version string is kept in sync by hand. The DCP plugin needs no v2 TUI entry: `opencode-dcp` auto-loads its TUI companion through its package `./tui` export, so `cli.json` has no `plugins` array - it carries only TUI client settings (theme, session, tabs, scroll). The plugin and its options live inline in `opencode.jsonc`'s `plugins` entry.
- `package.json` - plugin-authoring deps `@opencode-ai/plugin` (v1) and `@opencode/plugin` (v2, used on the v2-port branch).
- `profiles/` - profile overlays. Each subdir holds an authored `tiers.json` (tier entries of the form `{model, description}` plus the agent -> tier mapping; tier names are profile data, so any set is allowed) and a GENERATED `opencode.jsonc` that `scripts/tiers-sync.mjs` expands from it; consumers (bootstrap injection, profile switcher, config validation) read the tier names, order, and descriptions from that file rather than hardcoding them. opencode deep-merges the overlay on top of the base config when launched with `oc <profile>`, and `bin/oc` re-runs the sync before launching, so edit `tiers.json`, never the overlay. `default/` pins every agent to `opencode-go/deepseek-v4.1-flash#max` except the vision tier (`opencode-go/glm-5.3-flash`); `cheap-local/` pins every agent to Amenable Thor 1/qwen38-flash-next (local internal-IP provider); `nightsense/` uses the OpenRouter models. In-session switching (no restart) is handled by the `profile-switcher` plugin: it applies the model subset of an overlay as live agent transforms, keeps the per-directory records in `.active-profile` in sync with `bin/oc`, and surfaces a per-window `/profile` command + sidebar indicator in the TUI. Travel with the repo via `git pull`.
- `install.sh` - bootstrap script for multi-machine deployment. Checks codegraph is on PATH, runs `npm install` for local deps, reminds about env-var API keys. Idempotent. See `README.md` for the deploy recipe.
- `bin/oc` - bash wrapper that launches opencode under a profile overlay by setting `OPENCODE_CONFIG`. Subcommands: `oc [profile]`, `oc profile list|current|switch|add|delete|rename|install`, `oc completion <shell>`. Symlinked onto PATH by `install.sh`. Related file: `skills/create-profile/SKILL.md` (profile-management skill).
- `README.md` - deployment recipe and secret-handling notes for cloning this config to a new machine.

## Gitignore policy

`.gitignore` ignores `node_modules` and `bun.lock`. Everything else - including `package.json`, `package-lock.json`, and `.gitignore` itself - is committed. This makes the config dir self-contained for multi-machine deployment: a fresh clone plus `./install.sh` (see `README.md`) installs the local plugin-authoring dependencies (`@opencode-ai/plugin`, `@opencode/plugin`) and checks the codegraph MCP dependency. Do not re-add `package.json` or `package-lock.json` to `.gitignore` - the deployment flow depends on them being tracked.

## Editing this repo

- There is no build/test/lint for config. Verification = start a new OpenCode session (config and agent/skill definitions load at session start; some plugin changes need a restart).
- `package.json` is committed (see Gitignore policy above). The dependencies are the plugin-authoring packages `@opencode-ai/plugin` (v1) and `@opencode/plugin` (v2); `./install.sh` runs `npm install` to populate `node_modules` for plugin authoring on each deployed machine.
