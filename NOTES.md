# NOTES - fusion-tools implementation

## Goal
Implement two OpenCode v2 plugin features as one local package plugin-src/fusion-tools: (1) advisor - oh-my-pi style reviewer watching build/plan sessions, injecting notes via a global advise tool; (2) fanout - parallel worktree worker fan-out with schema-validated results. User decisions: advisor model opencode-go/deepseek-v4.1-flash (under cheap-local profile the advisor overrides to the local qwen modal), advisor scope build+plan; fanout v1 retains worktrees+patches (no auto-merge); pi-lumo provider DROPPED.

## Decisions
- Trigger advisor reviews via ctx.session.hook("context") (reliable per-provider-turn seam), NOT lossy session.idle/step events (idle is ephemeral).
- One advisor session per primary, mutex per primary, review timeout + ctx.session.interrupt.
- Emission guard ported from oh-my-pi: NFKC normalization, phrase blocklist, rank-aware dedupe (4096 FIFO), budget 4 non-blockers per review (blockers exempt).
- Redaction before sending transcript delta to advisor: elide tool results + regex pass (secrets must not reach the second model raw).
- Routing: mid-turn only blockers steer immediately, concerns held + reconfirmed next review; at turn end concern/blocker steer (may wake idle), nit = silent synthetic aside.
- Fanout: workers = ctx.session.create({agent, location:{worktree dir}}); results via submit_result tool (tool execute context HAS sessionID - verified in @opencode/schema/dist/tool.d.ts Tool.Context); integration v1 = retain worktrees + patch paths, parent applies.
- Config via plugins entry options (or fallback plugin-local config.json - record which below); runtime state in ctx.storage if available, else in-memory + documented.
- Sessions created by the plugin carry metadata provenance and are hard-gated from advisor triggers (no self-review recursion).
- Phase 0 finding: Promise plugins in 2.0.18 CANNOT write to the opencode log file (console.log is not captured; no log/log domains on context - upstream issue #27285, fix PR #29163 closed unmerged). Only the Effect plugin API (Effect.logInfo via @opencode/plugin/effect) reaches the log file. Phase 1 must either use the Effect API or keep structured JSON logging solely for stderr of foreground runs (opencode run --standalone --print-logs) and treat log-file logging as unavailable for observable plugin state (use state artifacts instead).
- Phase 1 implemented per spec; live e2e outcome: trigger -> delta -> advisor session -> prompt admitted -> advisor run + wait proven live (model stayed silent twice, legitimate); ctx.storage persistence and hot-reload rehydration both confirmed.
