# REPO.md - development rules for this repository

## Layout

- `opencode.jsonc` - main config: providers, per-agent models/variants, plugins list, MCP servers, `experimental.subagent_depth: 2`.
- `agents/*.md` - agent definitions (frontmatter + prompt body). `orchestrator.md` is the PRIMARY main agent (the single entrypoint and `default_agent` in `opencode.jsonc`); its body is the system prompt fed to the main agent every session. The roster is three capability shells: `sidekick` (execution, visual work, commits), `analyst` (read-only generalist: exploration, research, planning, visual inspection, red-team), and `reviewer` (audit gate). The built-in `build`/`plan` primaries are disabled in `opencode.jsonc`. Editing these changes every future session. `analyst.md` is the read-only generalist; its model comes from the `agents.analyst` pin in `opencode.jsonc`, and its permissions grant the ddgs MCP tools and a deny-by-default shell.
- `skills/<name>/SKILL.md` - skill definitions: `create-profile`, `fusion-brainstorming`, `fusion-code-review`, `fusion-commit`, `fusion-delegation-spec`, `fusion-plan-log`, `fusion-planning`, `fusion-research-methodology`, `fusion-sparring`, `fusion-workflow`, `plan-review`, `reflect`, `simplify`. The `fusion-*` skills carry the method knowledge and dispatch templates (including `templates/commit-task.md`, the guarded commit/push execution spec, and `templates/plan-task.md` / `templates/sparring-task.md` for analyst dispatches); agent bodies stay thin shells. `fusion-workflow` is the how-to map: entry points (orchestrator primary, read-only subagents), which skill to load when, and the delegation flow.
- `command/` - custom command directory (slash commands); currently holds `quick.md` only. Drop new command files here.
- `plugin-src/fusion-audit/` - local plugin package (deps installed via install.sh, registered as `./plugin-src/fusion-audit` in opencode.jsonc) holding the read-only observability plugin for the Fusion delegation tree. Logs subagent spawns and edit/task tool calls to OpenCode logs under service `fusion-audit`. It does NOT enforce who-does-what; permissions do that.
- `plugin-src/fusion-bootstrap/` - local plugin package (deps installed via install.sh, registered as `./plugin-src/fusion-bootstrap` in opencode.jsonc) that injects a short skill reminder as an extra system part on every primary model request: primaries (orchestrator) are told to check the skill catalog and fill a dispatch template from `skills/fusion-delegation-spec/templates/` instead of freehanding a task spec, and child sessions (any session with a structural `parentID`; detection is cached, a failed lookup injects nothing and retries next request) are told their task prompt is the full specification and their report must open with a `SKILLS:` line. Primaries also receive the tier table of the profile for the session's own directory (launched overlay > `OC_PROFILE` > that directory's `location` record > last global record > `default`, resolved through the same shared module as the profile switcher and subagent cap; a record naming a profile without `tiers.json` is skipped as stale); a tier whose authored model is empty renders as `unavailable` and the primary is told not to route work that needs that modality to any model and to tell the user.
- `plugin-src/fusion-channel/` - local plugin package (registered as the plain string `./plugin-src/fusion-channel` in opencode.jsonc) holding the steer/report channel: one `/steer` entry point (bare `/steer` opens a picker over the session's direct children with running first, then prompts for the message, while `/steer [agent|session-id] <message>` delivers directly; both call the server-side `steer` RPC registered by the plugin, and a model-callable `steer` tool is the non-TUI path for the same delivery logic - the server deliberately does NOT register a `/steer` command because keymap slash commands and server commands share one prompt completion list, so two registrations would show two entries; every steer appends a `type:"steer"` line to the durable JSON-lines channel log at `~/.local/state/opencode/fusion-inbox.jsonl` and surfaces a synthetic aside to the orchestrating session; the `report` tool writes child -> orchestrator notes/questions/blockers to the same log and mirrors them live; the module is always on).
- `plugin-src/shared/` - shared, dependency-free modules imported by the plugins and directly testable in plain node: `active-profile.js` resolves the active profile with one precedence order for the fusion-bootstrap tier table, profile-switcher, and subagent-cap (launched `OPENCODE_CONFIG` overlay > `OC_PROFILE` when usable > this directory's canonical `location` record > raw `location` record > last usable global record > `default`; unusable names are skipped so a stale record never shadows a usable profile) and parses `.active-profile` format v1 read-only.
- `plugin-src/profile-switcher/` - local plugin package (deps installed via install.sh, registered as the plain string `./plugin-src/profile-switcher` in opencode.jsonc) for in-session profile switching: the server entry (`index.ts`, plugin id "profile-switcher") exposes the `profile` RPC (list/current/set/populate + `changed`/`populate` events), resolves the active profile through `plugin-src/shared/active-profile.js` (launched overlay > `OC_PROFILE` > per-directory record > global record > `default`), applies the model subset of `profiles/<name>/opencode.jsonc` overlays as live agent-model transforms with availability fallback, and persists state per window location in `<CONFIG_DIR>/.active-profile` (format v1: an optional machine-wide `global\t<name>` fallback plus one `location\t<absDir>\t<name>` record per directory; the file is shared with `bin/opencode-profile`, and a `changed` broadcast converges only instances whose directory matches); `tiers.ts` runs the same `scripts/tiers-sync.mjs` expansion a tier-managed profile needs before a switch or a plain launch applies, a failed switch sync refuses the switch without persisting state, and a failed launch sync only logs and applies the existing overlay; on a switch it rewrites tracked sessions' persisted models to the new profile's targets via `session.switchModel`, scoped by TUI window claims (the open tabs) plus this location's `session.created` entries - never another workspace's history - and consent-gated to sessions matching the previous profile's target, with running sessions keeping theirs until idle; the TUI entry (`./tui`, plugin id "profile-switcher.tui") adds the `/profile` slash command, the per-window sidebar `Profile: <active>` indicator, and seeds the location's pre-existing sessions into the server tracker via the populate RPC at setup (relayed through the plugin event bus; `changed` events from other directories are ignored).
- `plugin-src/subagent-view/` - local plugin package (TUI-only; server entry is a no-op stub) that restores the v1-style live subagent visibility removed in v2: a collapsible `Subagents (n)` section in the sidebar (sidebar.content slot, mirrors the built-in MCP section's collapse pattern) listing child sessions of the open session as two-line rows - line 1 is the status marker, agent, and task title (an `@<agent> subagent` title prefix is stripped); line 2 is the model, live token/context usage (`tokens (%)`) and cost (2s polling; network calls only while a child runs). Rows open the child session on click (router navigate - children are not tab-openable), header keeps the true child total, all children are listed and the sidebar's own scrollbox handles overflow.
- `plugin-src/subagent-cap/` - local plugin package (deps installed via install.sh, registered as an options object in opencode.jsonc) that caps concurrent subagent spawn-tool calls per resolved active profile: options `{max, profiles}` where `max: 0` (the base config value) is unlimited and `profiles["cheap-local"] = 3` caps that overlay; a blocked spawn throws `Tool.Error` with the running/cap counts and the profile name so the calling agent sees why. The counter is per server instance (another window's spawns bypass it).
- `.plans/` (in target projects; never tracked, excluded via `.git/info/exclude`) - per-branch plan/notes document `<branch>.md`: approved plan steps, decisions, progress log, implemented features, open issues, final summary. This repo itself keeps its own plan logs under `.plans/` (archived ports live in `.plans/archive/`).
- `cli.json` - TUI client settings only (theme, session, tabs, scroll). It has no `plugins` array: `opencode-dcp` auto-loads its TUI companion through its package `./tui` export, and the plugin plus its options live inline in `opencode.jsonc`'s `plugins` entry.
- `package.json` - plugin-authoring deps `@opencode-ai/plugin` (v1) and `@opencode/plugin` (v2, used on the v2-port branch).
- `profiles/` - profile overlays. Each subdir holds an authored `tiers.json` (tier entries of the form `{model, description}` plus the agent -> tier mapping; tier names are profile data, so any set is allowed) and a GENERATED `opencode.jsonc` that `scripts/tiers-sync.mjs` expands from it; consumers (bootstrap injection, profile switcher, config validation) read the tier names, order, and descriptions from that file rather than hardcoding them. The shipped `tiers.json` files also map the hidden `compaction` agent to the `small` tier; the base config leaves it unset, so an unconfigured profile - and `default`, which mirrors the base pins - compacts with the session model. opencode deep-merges the overlay on top of the base config, and the `profile-switcher` plugin resolves and applies the active profile at startup (plain `opencode`; `OC_PROFILE=<name>` is a launch-only override), so edit `tiers.json`, never the overlay; a hand-edited `tiers.json` is synced on the next `./install.sh`, `opencode-profile add`, profile switch, or plain `opencode` launch (`OPENCODE_CONFIG` launches skip it). `default/` pins every agent to `opencode-go/deepseek-v4.1-flash#max` except the vision tier (`opencode-go/glm-5.3-flash`); `cheap-local/` pins every agent to Amenable Thor 1/qwen38-flash-next (local internal-IP provider) and ships its vision tier with an empty model (unavailable: that model cannot see images); `nightsense/` uses the OpenRouter models. In-session switching (no restart) is handled by the `profile-switcher` plugin: it applies the model subset of an overlay as live agent transforms, keeps the per-directory records in `.active-profile` in sync with `bin/opencode-profile`, and surfaces a per-window `/profile` command + sidebar indicator in the TUI. Travel with the repo via `git pull`.
- `install.sh` - bootstrap script for multi-machine deployment. Checks codegraph is on PATH, runs `npm install` for local deps, reminds about env-var API keys. Idempotent. See `README.md` for the deploy recipe.
- `bin/opencode-profile` - bash profile MANAGEMENT tool: it never launches opencode. Subcommands: `opencode-profile list|current|switch [--global] <name>|add <name> [--clone <src>] [--swap-model "<provider>/<model>[#variant]"]|delete <name>|rename <old> <new>`. `switch` and `add` sync a tier-managed profile's generated overlay first (a failed sync aborts before any state write). Symlinked onto PATH by `install.sh`, which also removes a stale `oc` launcher symlink; the old `oc` launcher, `oc profile install` bundle command, and `oc completion` are gone - plain `opencode` applies the active profile and `OC_PROFILE=<name> opencode` is the one-off launch. Related file: `skills/create-profile/SKILL.md` (profile-management skill).
- `scripts/` - maintenance scripts: `tiers-sync.mjs` generates profile overlays from `tiers.json` (`--check --all` reports drift), `validate-config.mjs` statically validates the config (17 checks, 0 failures expected), `check-opencode-version.sh` enforces the opencode >= 2.3.0 minimum (`--quiet` for install.sh), and `scripts/test/` holds their `node:test` suites. Run everything with `npm test`.
- `README.md` - deployment recipe and secret-handling notes for cloning this config to a new machine.

## Gitignore policy

`.gitignore` ignores `node_modules` and `bun.lock`. Everything else - including `package.json`, `package-lock.json`, and `.gitignore` itself - is committed. This makes the config dir self-contained for multi-machine deployment: a fresh clone plus `./install.sh` (see `README.md`) installs the local plugin-authoring dependencies (`@opencode-ai/plugin`, `@opencode/plugin`) and checks the codegraph MCP dependency. Do not re-add `package.json` or `package-lock.json` to `.gitignore` - the deployment flow depends on them being tracked.

## Editing this repo

- There is no build step for config. Verification: `node scripts/validate-config.mjs` (static checks, expect 17 checks / 0 failures), `node scripts/tiers-sync.mjs --check --all` (profile overlays in sync), `npm test` (node:test suites for tier sync, plugins, and scripts), then start a new OpenCode session (config and agent/skill definitions load at session start; some plugin changes need a restart).
- `package.json` is committed (see Gitignore policy above). The dependencies are the plugin-authoring packages `@opencode-ai/plugin` (v1) and `@opencode/plugin` (v2); `./install.sh` runs `npm install` to populate `node_modules` for plugin authoring on each deployed machine.
